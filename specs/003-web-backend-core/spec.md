# Спецификация: Архитектура бэкенда, API и Веб-ядра (003-web-backend-core)

## Обзор и контекст
Для того чтобы нативное Android-приложение (разработанное в фичах 001 и 002) могло успешно функционировать, бэкенд-архитектура и веб-интерфейс должны предоставлять соответствующую серверную инфраструктуру. Веб-часть должна бесшовно определять, что она запущена внутри мобильного контейнера, автоматически отправлять сгенерированные токены FCM в сессию пользователя, передавать контекст открытых чатов обратно в Android-оболочку и предоставлять REST API для синхронизации данных.

## Пользовательские сценарии и сценарии приемки
### Сценарий 1: Автоматическое определение Android-оболочки и инъекция моста
- **Дано:** Пользователь открывает веб-приложение внутри нативного WebView-контейнера.
- **Когда:** Загружается главная страница ядра веб-фронтенда.
- **Тогда:** Скрипты веб-ядра должны автоматически проверить наличие глобального объекта `window.AndroidBridge`.
- **И:** При его обнаружении активировать гибридный режим работы приложения, скрывая нативные элементы браузера (например, внешние шапки или кнопки скачивания сторонних APK).

### Сценарий 2: Прием FCM токена и его сохранение в базу данных через API
- **Дано:** Нативный контейнер Android вызывает колбэк-функцию `window.onFcmTokenUpdated(token)`.
- **Когда:** Веб-приложение получает строку токена и пользователь авторизован в системе.
- **Тогда:** Веб-фронтенд должен выполнить асинхронный аякс-запрос (POST) на серверный эндпоинт `api/update_user_fcm_token.php`.
- **И:** Серверный бэкенд-скрипт обязан обновить запись текущего пользователя в таблице базы данных, привязав актуальный токен для последующей отправки пушей.

### Сценарий 3: Передача контекста чата в Android при навигации по сайту
- **Дано:** Пользователь перемещается по страницам веб-приложения внутри WebView.
- **Когда:** Пользователь заходит на страницу диалога `group.html?id=125` или выходит из неё.
- **Тогда:** Веб-скрипт должен автоматически вызвать метод моста `window.AndroidBridge.setActiveChat(...)`, передав JSON с текущим `chatId` (или `null`), обеспечивая работу нативного фильтра подавления пушей.

## Функциональные требования
- **FR-301 (Глобальные JS-колбэки):** Веб-ядро должно объявлять функции `window.onFcmTokenUpdated` и `window.onImageSelected` на самом раннем этапе инициализации DOM, гарантируя готовность к приему фоновых событий из Android.
- **FR-302 (API Эндпоинт сохранения токенов):** Серверная часть должна содержать скрипт `api/update_user_fcm_token.php`, принимающий параметры `userId` и `fcm_token`, валидирующий сессию и сохраняющий данные в структуру СУБД.
- **FR-303 (Схема Базы Данных):** База данных должна содержать модифицированную структуру таблицы пользователей с поддержкой поля `fcm_token` (VARCHAR) для хранения уникальных адресов пуш-уведомлений.

## Критерии успеха (измеряемые и технологически независимые)
- **SC-501 (Надежность связывания сессий):** 100% валидных запросов обновления токенов от авторизованных сессий должны успешно обрабатываться API и сохраняться в СУБД в течение не более 200 мс.
- **SC-502 (Бесшовная адаптация UI):** При переключении флага гибридного режима веб-интерфейс должен полностью перестраивать структуру меню (убирать веб-навигацию) за время менее 50 мс, не вызывая мерцания экрана.

## Допущения и границы системы
- Веб-сервер поддерживает работу с СУБД MySQL / PostgreSQL и интерпретатором серверного кода.
- Сессионные данные пользователей защищены встроенным механизмом авторизации (сессионные куки или JWT-токены).
- **Вне рамок спецификации:** Настройка SSL-сертификатов сервера и детальная верстка страниц чата.
